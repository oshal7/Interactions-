How it's built

A fake desktop, real physics.

The original sells a Mac app by turning its own landing page into a cluttered desktop. You don't read about the clutter, you get to move it. Underneath it's a handful of ideas: a stage, absolutely-positioned windows, pointer events, a z-index counter, and (in this rebuild) a small animation loop for momentum, tilt and the put-away animation.

Ingredients

  • A positioned stageposition: relative; overflow: hidden. Every window is absolutely positioned inside it.
  • Pointer eventsOne code path for mouse, touch and pen: pointerdown / move / up.
  • Pointer capturesetPointerCapture keeps the drag going even if the pointer outruns the window.
  • touch-action: noneStops the phone from scrolling the page when you drag a window.
  • A z-index counterEach press sets z-index = ++top. That's the whole "bring to front".
  • Transforms, not left/toptranslate() moves on the GPU without re-layout, so dragging stays at 60fps.
  • requestAnimationFrame loopRuns only while something moves: momentum, tilt spring, glides.
  • Velocity samplingThe last ~80ms of pointer positions gives a throw speed and the tilt direction.
  • backdrop-filterFrosted menu bar and popover, like the real macOS chrome.
  • Keyboard supportWindows are focusable; arrow keys move them, and the tray works with Tab + Enter.

Each window is just a box with a centre point

Windows store their centre (x, y) plus rotation and scale. Rendering is a single transform, so rotating and scaling always happen around the middle of the window. Starting positions are fractions of the stage (0–1), so the layout survives resizing.

el.style.transform =
  `translate(${x - w / 2}px, ${y - h / 2}px) rotate(${rot}deg) scale(${scale})`;

Drag: remember where you grabbed it

On press we store the offset between the pointer and the window's centre, then on every move set the centre to pointer − offset. Without the offset, the window would jump so its centre snaps to your cursor.

win.el.addEventListener("pointerdown", (e) => {
  win.el.setPointerCapture(e.pointerId);
  win.el.style.zIndex = ++topZ;              // bring to front
  const p = toStage(e);
  win.grab = { dx: p.x - win.x, dy: p.y - win.y };
});
win.el.addEventListener("pointermove", (e) => {
  if (!win.grab) return;
  const p = toStage(e);
  win.x = p.x - win.grab.dx;
  win.y = p.y - win.grab.dy;
});

Throw: measure the flick, then let friction win

We keep the last few pointer samples. On release, the distance travelled over the last ~80ms is the window's velocity. Each frame the window moves by that velocity, and the velocity shrinks by the Glide factor. Multiplying by dt / 16 keeps it the same speed on 60Hz and 120Hz screens.

const f = Math.pow(config.glide, dt / 16);   // friction per frame
win.vx *= f;  win.vy *= f;
win.x += win.vx * dt;
win.y += win.vy * dt;

// wall hit: clamp, flip direction, lose some energy
if (win.x < minX) { win.x = minX; win.vx = -win.vx * config.bounciness; }

Tilt: lean into the movement, spring back after

The window's target angle is its horizontal speed times Tilt strength, capped at Max tilt. Instead of jumping there, the angle eases 20% of the way each frame. That smoothing is what makes it feel like it has weight. When you stop moving, the target goes back to 0 and it settles flat.

const target = clamp(win.vx * 20 * config.tiltAmount, -config.maxTilt, config.maxTilt);
win.rot += (target - win.rot) * 0.2;

Put away / bring back: glide to a target

"Put windows away" saves every window's position, then gives each one a target at the tray icon: scale 0.05, opacity 0, and a staggered delay so they leave one after another. The same easing step moves them (value += (target − value) × k). "Bring back" just swaps the targets for the saved positions. Arranging (tidy, pile, cascade, scatter) reuses the same mechanism with different targets.

windows.forEach((win, i) => {
  win.home = { x: win.x, y: win.y };
  glideTo(win, { x: tray.x, y: tray.y, scale: 0.05, alpha: 0 }, i * config.stagger);
});

Only animate when something is moving

The requestAnimationFrame loop starts on the first press or glide and stops itself once every window is still. An idle page uses no CPU, and nothing fights with the pointer handlers. With prefers-reduced-motion, throws and glides finish instantly.
